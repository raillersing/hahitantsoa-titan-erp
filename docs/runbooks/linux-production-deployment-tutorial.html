Déployez votre ERP sur Linux, sans perdre le fil.

Un guide pas à pas pour mettre en service l’application sur un serveur AMD64 ou ARM64, avec HTTPS, données persistantes, sauvegarde et vérification de restauration.

Compatible
Linux AMD64 et ARM64 — images Docker multi-architecture.
Isolé
PostgreSQL, Redis et Django ne sont pas exposés au réseau public.
À prouver avant ouverture
DNS, HTTPS, restauration et recette métier sur le serveur réel.
⚠
Ce guide concerne un nouveau serveur Linux. Les fichiers production.env et les sauvegardes restent exclusivement sur le serveur. N’écrivez ni mot de passe, ni clé, ni dump de base dans Git, un ticket ou un message.

00

Avant de commencer

Définir le cadre avant toute commande.

Ce que ce déploiement installe

Caddy (HTTPS) → interface Nginx → Django/Gunicorn → PostgreSQL + Redis. Les données et médias utilisent des volumes Docker persistants.

Ce qu’il ne fait pas

Il ne remplace pas le pilote macOS, ne crée pas les secrets pour vous et ne rend pas l’application publique sans domaine fonctionnel.

01

Préparer le serveur Linux

Le serveur doit être maintenu et réservé à cette pile.

Connectez-vous avec un compte administrateur du serveur. Installez Docker Engine et le plugin Docker Compose selon la documentation officielle de votre distribution. Vérifiez ensuite :

terminal Linux
docker --version
docker compose version
docker info

Résultat attendu

Les trois commandes répondent sans erreur. Docker est démarré et votre utilisateur possède les droits nécessaires.

À vérifier avec l’hébergeur

Stockage durable, mises à jour de sécurité du système, pare-feu et accès SSH limité aux personnes autorisées.

02

Connecter le domaine et le réseau

Caddy obtient automatiquement le certificat HTTPS seulement si le DNS et les ports sont corrects.

DNS

Créez un enregistrement A vers l’IPv4 publique du serveur ; ajoutez un AAAA si IPv6 est utilisé. Exemple : erp.votre-domaine.tld.

Pare-feu

Autorisez TCP 80 et 443, ainsi qu’UDP 443. N’ouvrez pas PostgreSQL (5432), Redis (6379) ni Django (8000).

Pourquoi le port 80 reste-t-il nécessaire ?

Il permet à l’autorité de certification de vérifier le domaine et de rediriger proprement les visiteurs vers HTTPS. Il n’expose pas les services internes.

03

Créer la configuration secrète

La configuration est locale au serveur et protégée par les permissions du système.

Placez le dépôt à la version approuvée sur le serveur, puis ouvrez le répertoire de déploiement :

terminal Linux
cd /chemin/vers/hahitantsoa-titan-erp/deploy/linux
cp production.env.example production.env
chmod 600 production.env

Dans production.env, remplacez le domaine d’exemple et chacune des valeurs REPLACE_WITH_A_LONG_RANDOM_VALUE par des valeurs longues et aléatoires, enregistrées dans votre gestionnaire de mots de passe.

Doit rester activé

DJANGO_DEBUG=False, les cookies sécurisés, la redirection HTTPS et la confiance proxy sont déjà préconfigurés dans le modèle.

Ne jamais faire

Ne versionnez pas production.env et ne remplacez jamais les valeurs par un mot de passe mémorisable ou partagé dans un chat.

04

Démarrer la pile de production

La migration s’exécute avant le démarrage du backend.

terminal Linux
docker compose --env-file production.env -f compose.yaml up -d --build
docker compose --env-file production.env -f compose.yaml ps

Attendez que db, redis et backend indiquent healthy. Le service migrate peut terminer avec succès : c’est son rôle normal.

Un service n’est pas healthy

Ne passez pas à l’étape suivante. Consultez les journaux du seul service concerné avec docker compose --env-file production.env -f compose.yaml logs --tail=200 NOM_DU_SERVICE. Ne publiez jamais le contenu d’un fichier de configuration dans ces journaux.

05

Vérifier et créer le premier administrateur

La pile est prête seulement lorsque ses dépendances et sa configuration de sécurité répondent correctement.

terminal Linux
curl --fail --silent --show-error https://erp.votre-domaine.tld/healthz/
curl --fail --silent --show-error https://erp.votre-domaine.tld/readyz/
docker compose --env-file production.env -f compose.yaml exec backend python backend/manage.py check --deploy
docker compose --env-file production.env -f compose.yaml exec backend python backend/manage.py createsuperuser

Interprétation

/healthz/ confirme le processus ; /readyz/ confirme PostgreSQL et Redis ; le check Django confirme les réglages de déploiement.

Premier accès

Ouvrez le domaine en navigation privée, connectez-vous avec le compte créé puis déconnectez-vous. Ne conservez pas ce mot de passe dans l’historique du terminal.

06

Sauvegarder et prouver la restauration

Une sauvegarde non restaurée n’est pas une preuve de reprise.

terminal Linux
./backup.sh
./restore-verify.sh backups/postgres-AAAAMMJJTHHMMSSZ.dump

backup.sh produit un dump PostgreSQL avec des permissions restrictives. Copiez-le immédiatement vers un stockage chiffré, hors du serveur. restore-verify.sh restaure ce dump dans une base PostgreSQL éphémère, sans volume ni port de production, puis vérifie la présence du schéma.

⛨
Règle absolue : ne lancez jamais une restauration sur la base de production pour « tester ». Le script de vérification existe précisément pour éviter cette erreur.
07

Décision d’ouverture

Cette dernière revue évite une mise en service prématurée.

Vous pouvez ouvrir aux utilisateurs si…

DNS/HTTPS, services healthy, check Django, création admin, connexion, sauvegarde hors site et restauration vérifiée sont tous validés.

Attendez si…

Un seul contrôle est manquant, si le certificat n’est pas valide, ou si la restauration n’a pas été prouvée. Corrigez d’abord, puis reprenez cette checklist.

Mise à jour future et retour arrière

Avant toute mise à jour : sauvegardez, notez le SHA actuellement déployé, déployez uniquement un SHA approuvé, puis rejouez les vérifications. N’utilisez jamais docker compose down -v : cette commande détruirait les volumes de données et médias.
